### P1-1 自动重排模式删除结合点后不紧凑（编号规则功能整体失效）
- 类型：功能缺陷｜状态：已实测复现（复现 3+ 次，稳定）
- 用例：V33/T8b/T17b｜首次确认版本：f507a49｜web/lib/edge-labels.js:301,304、src/server.js:1638、web/lib/label-panel.js:105-107
- 最小输入：标签编号模式设为"自动重排"，画布 ≥2 个结合点，删除其中 1 个。
- 预期：剩余结合点自动紧凑为 1..n（i18n `label.mode.hint` 明示承诺）。实际：`[1,2]` 删除 1 后剩 `[2]` 永不紧凑；`labels.renumber` 事件数 0；跳号持久化到 overlay（刷新后依旧）。
- 根因链：afterConnDelete 产出 `{key,id,num}` → /api/labels/renumber 逐项校验 `typeof it.edgeKey !== 'string'` → 400「items 每项要带 edgeKey 与 id」→ label-panel.js:107 不检查返回值，失败静默。已有防护不足：labels-api.test.js 只测服务端契约，前端→API 集成无测试。
- 反证：以 `edgeKey` 字段直连服务端 → `{ok:true,changed:1}` 且编号生效（服务端完好）。对照：固定模式挑空缺号正常。
- 用户影响：自动重排这一常用标签工作流在 GUI 全链路失效，错误编号随 overlay 落库并进入导出。
- 最小修复方向：统一字段名（前端改产 `edgeKey`，连带 core/labels.js compactConnEntries 与 labels.test.js 断言一起改；或服务端收 `key` 别名，二选一定死）；补前端→API 集成测试；顺手在 label-panel 提交处补失败呈现（与 P3-9 同族）。
- 不应扩展：不需要重排算法改动。

### P2-1 CALLGRAPH_DB 环境变量残留时桌面版读写错误数据库
- 类型：功能缺陷（数据落错库）｜状态：已实测复现（真实 Electron，5/5 子项）
- 用例：S27/R1/W4-T7｜src/core/store.js:176-182、electron/main.cjs:131
- 最小输入：设全局 `CALLGRAPH_DB=<临时>\x.db` 后启动 `electron .`，打开工程并标注。
- 预期：桌面版数据落 userData\callgraph.db。实际：`[存储]` 日志指向 x.db，标注写入 x.db（文件实存 4096B）；清除变量后重开，userData 库无该标注（用户感知"保存了重启就没了"）。
- 根因：resolveDbPath 中 `CALLGRAPH_DB` 优先于 `CALLGRAPH_USER_DATA`；main.cjs fork 时 `env: {...process.env}` 继承了用户环境残留。
- 反证：不设变量对照轮 5/5 正常落 userData。
- 最小修复方向：Electron fork 时显式覆盖 `CALLGRAPH_DB:''`（或 resolveDbPath 给 CALLGRAPH_USER_DATA 更高优先级）。
- 不应扩展：不需要改测试夹具注入方式（scripts/lib/server.mjs 用 CALLGRAPH_DB 是有意的）。

### P2-2 删除唯一入口节点后 Ctrl+Z 恢复失效
- 类型：功能缺陷（承诺的 20 秒恢复静默失效）｜状态：已实测复现
- 用例：V26b/W3a-1｜web/app.js:198-210,238-243,99-101；服务侧共因 src/server.js:1343-1351（默认入口不排除已删节点）
- 最小输入：视图仅一个入口（默认 main），选中该节点按 Delete，20 秒内按 Ctrl+Z。
- 预期：恢复被删节点。实际：删除后视图自动重选被删节点为默认入口，canRestoreDelete 的入口集合比对恒 false，且 loadView 已重置撤销栈——两条恢复路径同时失效（时间轴回看仍可救，路径深）。
- 根因链：删除入口后 `state.roots=[]` 记入 deleteStack（roots:''）；reloadKeepCam 后服务端默认入口又选出被删节点 → 比对必然不等。数据本身无丢失（delete 事件已落库）。
- 反证：多入口场景删除其一，恢复正常（V26）。
- 最小修复方向（二选一）：canRestoreDelete 对"记录 roots 为空"放宽为同工程内可恢复；或服务端默认入口挑选排除 overlay.deleted.nodes 中已删节点（S 复核确认可行且改动小）。
- 不应扩展：不需要重做删除栈设计。

### P2-3 `#if 0` 等未选中分支内的 `#define/#undef` 仍然全局生效
- 类型：功能缺陷（调用边错误归属）｜状态：已实测复现（2 次一致）
- 用例：A05/M1/W4-T1｜src/core/preproc.js:97-111（无条件入表）、212-248（展开不检查定义处 cond）
- 最小输入：`#if 0` + `#define G() foo()` + `#endif` + `void a(void){ G(); }`。
- 预期（真实 C 语义）：G 未定义，调用记为 G（ext::G）。实际：调用边变为 `a → ext::foo`（kind=macro, via=G）——编译产物中不存在的边，且原调用目标丢失。
- 用户影响：用 `#if 0` 注释掉配置/兼容宏的真实工程，调用图出现错边并漏边。嵌入式代码常见该模式，故定 P2。
- 反证：无守卫可拦（展开层不读 cond）；数据流侧不涉及。
- 最小修复方向：macros.set/delete 时若当前分支 cond 非"恒真"则打标，expandSeq 跳过带标宏（或按 cond 前缀过滤）。
- 不应扩展：不需要实现完整条件求值。

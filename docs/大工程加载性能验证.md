# 大工程加载性能验证

2026-10-26，Windows、Node.js 24，在独立临时数据库中验证，不读取私有工程。

## 公开案例与规模

- [Ultimate NAG52 固件](https://github.com/rnd-ash/ultimate-nag52-fw)：奔驰 722.6 变速箱控制器，提交 `e090b301cdf4ea1da12b2ca4f3fa81870435186f`，扫描整个仓库，共 174 个 C/C++ 源码及头文件。
- [rusEFI](https://github.com/rusefi/rusefi)：包含 `firmware/controllers/tcu` 变速箱控制代码，提交 `54d4fcdbae0a356d9c352ed7474f746109fb3116`，扫描 `firmware`，共 1658 个 C/C++ 源码及头文件；未拉取子模块。
- 自动生成的 C 工程：10000 个文件、20000 个函数、30000 条关系、10000 个变量，用于补足万文件规模。

公开源码只用于读取和分析，保存在忽略目录 `.verify-tmp/public/`，未并入产品，也未执行它们的构建脚本。公开工程包含 C++，这里的函数计数指当前分析器识别结果，不代表新增了完整的 C++ 语义支持。

## 修复内容

原缓存以展开后的 JSON 大小限制为 40 MB。rusEFI 的 JSON 约 124 MB，因此每次打开都无法命中缓存；即使小工程命中，AST 变量读写索引也会重新构建。

现在使用 Node 内置二进制序列化保存完整分析结果，包括 Map、Set 和变量读写行号；不保存 `_index` 引用表和 Promise。磁盘上按压缩后的大小限制，rusEFI 实际缓存约 11.0 MiB。缓存键已变更，旧的派生缓存会重新生成，标注和工程状态不受影响。

文件树只在展开或定位文件时创建该文件的函数行；未展开文件的勾选和入口顺序继续保留。加载日志也改为包含 AST 分析和缓存写入耗时，避免原日志少报等待时间。

## 实测结果

以下为同一源码、已有缓存后，重新启动独立服务进程，到服务就绪的墙钟时间；不包含 Electron 窗口启动与 ELK 出图时间。数字会受磁盘缓存、杀毒扫描和同时运行的程序影响，不能视为所有机器的保证值。

| 工程 | 优化前重开 | 优化后重开 |
| --- | ---: | ---: |
| Ultimate NAG52，174 文件 | 2.80 秒 | 0.35 秒 |
| rusEFI firmware，1658 文件 | 69.65 秒，无法命中缓存 | 1.75 秒 |
| 合成 C 工程，10000 文件 | 4.65 秒 | 2.02 秒 |

万文件文件树另测：每文件两个函数，首次构建含强制布局，从约 695 ms 降至 328 ms；DOM 元素从 110505 个降至 50505 个。

优化前后函数、关系和变量计数相同，变量接口明细的 SHA-256 相同。单元回归验证完整分析缓存的读写集合、函数体、关系和调用顺序建议；界面验证按需展开、定位、取消勾选及保留未展开文件的选择。原始测量记录保存在 `out/performance/`。

## 使用与边界

升级后第一次打开需要重建缓存。首次打开、源码修改后的全量分析仍可能较慢；本次没有加入逐文件增量解析。没有通过少扫描文件、截断变量或减少连线来换取加载速度。ELK 布局规则保持不变。
